# "User Account for Workstation" Window

> ASTER reference: https://dokwiki.ibiksoft.com/en/v3/core/gui/gui_logininfo

## What ASTER does

This window lets an administrator change the Windows login used for a given workplace and choose whether that workplace logs in automatically or shows a login prompt at startup. It adapts to the account type: for a domain account it takes a domain name, username, and password (with confirmation); for a local account it offers a dropdown of local accounts plus password/confirmation and a shortcut button into Windows' own "User accounts" tool. The local-account dropdown's default entry is **"Display login dialog"** rather than any specific account — meaning the workplace shows Windows' normal login prompt instead of auto-logging in; picking an actual account name from the dropdown switches to unattended auto-login using that account's stored credentials. A companion **"Force relogin"** action (on the workplace's own context menu, alongside this dialog) signs the current session out immediately so a changed account/login setting takes effect without waiting for a restart.

## OpenMultiSeat status

🚧 **Partially implemented.**

The Seats page has a real **"User Account…"** dialog (`UserAccountWindow`), reachable by selecting a seat: Local/Domain account type, a local-account dropdown populated from real Windows accounts (via WMI `Win32_UserAccount`, defaulting to **"Display login dialog"** exactly like ASTER), and password/confirmation fields. `Seat.WindowsUser`, `WindowsDomain`, `DisplayLoginDialog`, and `EncryptedPassword` are all real, persisted fields. A password, when set, is protected with Windows DPAPI (`SeatCredentialProtector`, `LocalMachine` scope) and stored base64-encoded — never in plaintext — with a round-trip verified in `tests/OpenMultiSeat.Tests/SeatCredentialProtectorTests.cs`, including that a password saved under the earlier `CurrentUser` scope (before the switch — see below) still decrypts. The password box never re-displays a saved plaintext on reopen (DPAPI ciphertext isn't reversible to plaintext for display purposes without decrypting it, and doing that just to populate a text box would be its own bad practice) — instead the label above it switches to "Password (already saved — leave blank to keep it, or enter a new one to replace it)" once `Seat.EncryptedPassword` is non-empty, so the saved credential's presence is visible without exposing it.

Credential-based process launching is now real and verified, via a **"Test Launch (Notepad)…"** button on the dialog: it calls the new `ISessionManager.LaunchProcessWithCredentialsAsync`, which wraps `CreateProcessWithLogonW` — the same mechanism behind Windows Explorer's "Run as different user". Confirmed end-to-end against the real API: a correct credential launches `notepad.exe` and returns its PID; a deliberately wrong password returns the exact expected Win32 error 1326 ("The user name or password is incorrect"), proving the P/Invoke marshaling and that the Secondary Logon (`seclogon`) service is active. `CreateProcessWithLogonW` is a Unicode-only API (`...W`, no ANSI counterpart) — it needed its own `STARTUPINFOW` struct (`CharSet.Unicode`) rather than reusing the existing ANSI `STARTUPINFO` used for `CreateProcessAsUser` elsewhere; reusing the ANSI struct would have compiled and run without erroring, but silently corrupted string fields like `lpDesktop`. Struct sizes (`STARTUPINFOW` = 104 bytes, `PROCESS_INFORMATION` = 24 bytes) were verified via reflection against real Win32 x64 sizes *before* relying on them, not after a crash.

**Auto-login is now wired to seat start** — the [General Settings tab](general-settings-tab.md)'s Workplace Start Mode setting (Manual / At System Startup / Via Workplace 1) calls `SeatStartupOrchestrator`, which reads `DisplayLoginDialog`/`EncryptedPassword` for every seat and, for each one with a saved login, calls the same `LaunchProcessWithCredentialsAsync` this dialog's "Test Launch…" button exercises. That closes the gap this section used to describe.

What's still deliberately **not** built, and remains a materially bigger and more security-sensitive piece than the configuration dialog, the test-launch capability, or the startup wiring above:

- **Not a hardware-isolated session.** `CreateProcessWithLogonW` starts a process running as the target user — it does **not** create a new interactive desktop session bound to a specific seat's own monitor/keyboard/mouse the way ASTER's multi-seat login does. True simultaneous multi-seat login (each seat showing its own separately-logged-in desktop, on its own hardware, at the same time) needs either Windows Server RDS/MultiPoint-Server-style session support or a Winlogon Credential Provider — neither exists in this codebase.
- **No "Force relogin" action.** Would need `SessionEnumerator`'s WTS APIs to terminate the seat's current session — not implemented.
- **DPAPI's real constraint, stated plainly:** `LocalMachine` scope (switched from `CurrentUser` specifically so the At-System-Startup scheduled task, which runs as SYSTEM, can decrypt seat passwords) means the encrypted password can be decrypted by **any** local process on this machine — any user account, not just the one that saved it. That's real to weigh: it's still far better than plaintext (a copy of `seats.json` alone, off this machine, is useless), but it's no longer a secret from other local accounts/administrators the way `CurrentUser` scope was. See [`SeatCredentialProtector`](../../src/OpenMultiSeat.Core/SeatCredentialProtector.cs)'s doc comment for the full reasoning.
